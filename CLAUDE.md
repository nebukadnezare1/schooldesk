## 1. Objectif du projet

Application web de gestion scolaire, à usage quotidien par un administrateur, une directrice et des professeurs — personnel non technique. Conçue à l'origine pour une école préscolaire (enfants 3-7 ans), le positionnement a été généralisé le 26/08 pour couvrir tout type d'établissement scolaire (voir Journal de session). Doit rester simple à l'usage tout en ayant une architecture solide et évolutive. Cahier des charges complet : [prompt-ecole-garden.md](prompt-ecole-garden.md) (référence faisant autorité pour toute fonctionnalité non encore implémentée — rédigé à l'origine avec un vocabulaire préscolaire, à lire avec cette bascule en tête).

**Depuis le 25/08, l'application est multi-tenant (SaaS)** : plusieurs écoles peuvent utiliser le même déploiement, chacune avec son espace totalement isolé, créé via une inscription en 3 champs (nom de l'école, email, mot de passe). Voir §5 pour le mécanisme d'isolation et §8 pour les décisions de conception.

**Nom de marque de l'interface (depuis le 26/08) : « SchoolDesk »** — ne pas confondre avec le nom du projet/dépôt (`ecole-garden`, dossier, services Docker, paquets npm `@ecole-garden/*`), qui reste inchangé et n'a aucune raison d'être renommé. Seul le texte affiché à l'utilisateur (titre d'onglet, logo dans la barre latérale, page de connexion, landing page, reçus) a été renommé. La donnée réelle « École Garden » (l'école bootstrap créée en base, `School.name`) n'a volontairement pas été touchée — l'utilisateur a précisé que cette école ne sera de toute façon pas présente sur le déploiement SaaS final (base vierge), donc ce n'est pas un problème à corriger ici. Voir détail dans le Journal de session.

## 2. Architecture actuelle

Monorepo npm workspaces, 3 conteneurs Docker :

```
PostgreSQL 16 (alpine) ── backend (Express/Prisma, port 3000) ── frontend (Vite build statique, port 8080)
```

- Le conteneur backend exécute automatiquement `prisma migrate deploy && npm run prisma:seed` à **chaque démarrage** (voir `apps/backend/Dockerfile`), avant de lancer le serveur. Le seed est idempotent (`upsert`), il ne recrée rien s'il existe déjà.
- **Tâche planifiée (27/08)** : `apps/backend/src/server.ts` lance `generateMonthlyMensualites()` (`apps/backend/src/monthly-fees-job.ts`) au démarrage du serveur puis toutes les 24h (`setInterval`, pas de dépendance externe type node-cron). Génère automatiquement, pour chaque élève actif et inscrit dans l'année active, le frais « Mensualité » du mois en cours (idempotent, upsert, ne touche jamais un frais existant) — sans quoi un élève dont la fiche n'est jamais rouverte n'aurait jamais de nouveau frais au changement de mois. Logique de calcul de la période (`monthlyFeePeriod` dans `apps/backend/src/fee-period.ts`) partagée avec `ensureStudentFees` (déclenché lui à la création/modification d'un élève) pour éviter toute divergence entre les deux chemins. **Comportement aux bornes de l'année** (clarifié avec l'utilisateur le 27/08) : la période est plafonnée (clamp) dans `[startsAt, endsAt]` de l'année active — avant le début de l'année, tout le monde est facturé pour son premier mois (ex. testé le 27/08 avec une année commençant le 01/09 : frais « Septembre » généré par avance) ; après sa fin, plus aucun nouveau frais n'est créé (la tâche « plafonne » sur le dernier mois, déjà existant) — pas de faux impayé generé pendant les vacances d'été. La reprise à la rentrée suivante reste conditionnée à une étape manuelle déjà existante et inchangée : créer la nouvelle année scolaire et la marquer « Active » (page Classes) — la tâche ne fait que suivre l'année déjà active, elle n'en crée jamais une nouvelle elle-même. Depuis le 27/08, la même exécution quotidienne fait aussi tourner `refreshOverdueStatuses()` (`apps/backend/src/overdue-job.ts`) : bascule en `OVERDUE` tout frais `UNPAID` dont l'échéance est passée, toutes écoles confondues — même correction que celle déjà appliquée à la volée par `GET /unpaid-fees`, mais désormais proactive (le Dashboard reflète les retards sans attendre qu'un humain ouvre Impayés en premier).
- **Le frontend est servi par Nginx depuis le 28/08** (`apps/frontend/Dockerfile`, multi-stage : Node compile `dist/`, puis image `nginx:1.27-alpine` qui le sert) et appelle toujours l'API en **même origine**, via `/api/...` (`apps/frontend/src/api-url.ts` → `apiUrl = ''`) — Nginx proxifie en interne `/api/` vers `http://backend:3000` (`apps/frontend/nginx.conf`, `proxy_pass` sans chemin donc l'URI d'origine est transmise telle quelle). Conséquence importante : **aucune adresse ni port de backend n'apparaît jamais dans le JavaScript envoyé au navigateur**, et un seul port doit être joignable pour utiliser l'app depuis n'importe où (PC, LAN, tunnel public) — celui du frontend (`FRONTEND_PORT`, 8080 par défaut). Remplace l'approche précédente du même jour (URL calculée à partir de `window.location.hostname`), devenue inutile. En dev sans Docker (`npm run dev`), le proxy intégré de Vite (`vite.config.ts`, `server.proxy['/api']`) joue le même rôle. `nginx.conf` gère aussi le routage SPA (`try_files ... /index.html`, `index.html` lui-même en `Cache-Control: no-cache` pour qu'un nouveau déploiement soit pris en compte rapidement) et le cache longue durée sûr des fichiers compilés à nom haché (`/assets/*`). **Important, corrigé après un premier oubli** : même si le navigateur voit tout en même origine, il envoie quand même l'en-tête `Origin` sur les requêtes POST/PATCH/DELETE, et le middleware CORS du backend (`apps/backend/src/server.ts`) le contrôle malgré tout côté serveur — `CORS_ORIGIN` doit donc être réglé sur l'adresse publique réelle du site (ex. `https://schooldesk.saas-app.eu`) dans le `.env` de tout déploiement autre que local, sans quoi le backend rejette la requête (500) avant même qu'elle atteigne une route. Ce n'est pas un simple filet de sécurité optionnel — voir `.env.example`, commentaire ajouté au-dessus de `CORS_ORIGIN`.
- Authentification par cookie de session HttpOnly (`ecole_garden_session`) ou header `Authorization: Bearer`, token aléatoire haché en SHA-256 côté base (`UserSession.tokenHash`), pas de JWT. Le cookie étant `HttpOnly`, React ne peut pas le lire : `App.tsx` restaure la session au montage via `GET /api/auth/me` (25/08) — ne jamais supposer que l'état `user` est fiable dès le premier rendu sans passer par cette vérification.
- Permissions vérifiées **côté backend uniquement** (middleware `requirePermission(code)` dans `apps/backend/src/auth.ts`) — jamais côté frontend seul.
- **Multi-tenant depuis le 25/08** : une seule base PostgreSQL partagée par toutes les écoles, isolation logique via une colonne `schoolId` sur chaque table métier. `authenticate()` attache `request.db` (client Prisma scopé à l'école de l'utilisateur connecté, via `apps/backend/src/tenant-db.ts`) sur chaque requête authentifiée — voir §5 et §8, règle impérative en §12.

## 5. Base de données et fonctionnement

Schéma complet dans `apps/backend/prisma/schema.prisma`. Points de conception à connaître avant toute modification :

- **Multi-tenant (25/08)** : modèle `School` (id, name) + colonne `schoolId` sur presque tout (`AcademicYear`, `SchoolClass`, `Student`, `Guardian`, `Employee`, `Attendance`, `EmployeeAttendance`, `Enrollment`, `FeeType`, `StudentFee`, `Payment`, `Expense`, `ExpenseCategory`, `Payroll`, `PayrollPayment`, `SalaryAdvance`, `CashTransaction`, `Setting`, `User`). **Exceptions volontaires** : `StudentGuardian`/`PaymentAllocation`/`RolePermission` n'ont pas leur propre `schoolId` (accédés uniquement via une relation parente déjà scopée) ; `Role`/`Permission` restent un catalogue **global** partagé par toutes les écoles (un seul rôle `ADMIN` existe à ce jour, voir plus bas) ; `User.email` reste **globalement unique** (pas composite avec `schoolId`) — décision délibérée pour que la connexion retrouve directement la bonne école sans étape de sélection (un email ne peut appartenir qu'à une seule école). Contraintes uniques devenues composites `(schoolId, X)` : `Student.matricule`, `Employee.matricule`, `AcademicYear.label`, `Payment.paymentNumber`/`receiptNumber`, `Expense.number`, `FeeType.name`, `ExpenseCategory.name`, `Setting.key`, `PayrollPayment.receiptNumber` (27/08, format `BUL-<année>-<00001>`, même principe que `Payment.receiptNumber`).
- **Isolation appliquée via `apps/backend/src/tenant-db.ts`**, pas en éditant chaque requête à la main : `forSchool(prisma, schoolId)` crée une Prisma Client Extension qui injecte automatiquement `schoolId` dans `where` (find/update/delete/count/aggregate/groupBy) et dans `data` (create/createMany) pour tous les modèles listés ci-dessus. `auth.ts` attache ce client scopé à `request.db` sur chaque requête authentifiée. **Règle impérative, voir §12** : toute route doit utiliser `request.db!` pour ces modèles, jamais le `prisma` brut — et toute création acceptant un ID étranger fourni par le client (`employeeId`, `academicYearId`, `schoolClassId`, `categoryId`, `guardianId`, `studentFeeId`, etc.) doit d'abord vérifier son appartenance à l'école avec `assertOwned(request.db, accessor, id)`, car l'extension seule ne empêche pas de « planter » un ID d'une autre école dans une création (la contrainte FK Prisma vérifie seulement que la ligne existe quelque part, pas qu'elle appartient à la bonne école).
- **Responsables séparés** : `Student <-> StudentGuardian <-> Guardian` (jamais de champs parent directement sur `Student`).
- **Historique scolaire** : `Student -> Enrollment -> SchoolClass -> AcademicYear`, jamais un simple `classId` sur l'élève.
- **Dû vs payé séparés** : `StudentFee` (ce qui est dû) est distinct de `Payment` + `PaymentAllocation` (versements réels). Un paiement peut couvrir plusieurs frais ; un frais peut recevoir plusieurs versements. **Aucun versement n'écrase le précédent.**
- **Montants par élève** (décision du 24/08, voir `sections/2026-08-24-frais-eleves.md`) : `Student.monthlyFee` et `Student.insuranceFee` pilotent le montant réellement dû pour cet élève ; `FeeType.defaultAmount` ne sert plus que de repli si l'élève n'a pas de montant configuré. Depuis le 26/08, ces deux montants sont obligatoires à la création (voir §6/§12) — le repli sur `FeeType.defaultAmount` ne s'applique donc plus qu'aux élèves créés avant cette date ou modifiés via `PATCH` (non durci). Les frais du mois en cours (mensualité) et de l'année (assurance) sont créés automatiquement à la création/modification de l'élève via `ensureStudentFees()` (upsert idempotent, ne touche jamais un frais existant).
- **Aucune suppression physique de donnée financière ou de personne** : `Student`/`Employee` → statut `ARCHIVED` ; `SchoolClass` → `INACTIVE` ; `Payment`/`Expense`/`PayrollPayment`/`SalaryAdvance` → annulation (`cancelledAt`/`cancelReason`/`cancelledById`), l'enregistrement original reste intact et visible (grisé/badgé) mais exclu des totaux (Caisse, Dashboard).
- **Versements de salaire** = table dédiée `PayrollPayment` (une ligne par versement, comme `Payment`). Corrigé le 24/08 — avant cela `Payroll.amountPaid` était incrémenté directement sans trace individuelle (défaut architectural corrigé avec rétro-remplissage en migration, voir `sections/2026-08-24-salaires.md`).
- **Caisse (`CashTransaction`)** : registre append-only relié à sa source via `(sourceType, sourceId)` unique. Ne jamais modifier le solde autrement qu'en insérant un mouvement source (paiement, dépense, salaire). Le modèle ne stocke ni élève ni classe ni employé directement : `GET /api/cash` (`operations-routes.ts`) enrichit chaque ligne à la volée (`linkedName`, `classId`, `className`) en résolvant `sourceType`/`sourceId` vers `Payment.student` (+ classe de son inscription active) ou `PayrollPayment.payroll.employee`, en deux requêtes groupées (pas de N+1). Sert de base au filtre par classe de la page Caisse (24/08).
- **Montants** : toujours `Decimal(12,2)`, jamais `Float`.
- **Permissions** : `Role` / `Permission` / `RolePermission` génériques (globales, voir plus haut) ; **seul le rôle `ADMIN` est actuellement seedé** avec toutes les permissions. Les rôles Directrice/Professeur du cahier des charges (§5) ne sont pas encore créés en base, bien que l'architecture les supporte déjà.
- Migrations, dans l'ordre : `init` → `auth` → `academic_years_classes` → `students_guardians_enrollments` → `employees_attendance` → `fees_payments` → `expenses_payroll_cash` → `payment_cancellation` (23/08) → `financial_cancellation` (24/08, dépenses+salaires+avances) → `student_fee_amounts` (24/08) → `multi_tenant_schools` (25/08, ajoute `School` + `schoolId` partout, migration écrite à la main via `prisma migrate diff` puis complétée d'un bloc de rétro-remplissage gardé, voir §8) → `payroll_payment_receipt_number` (27/08, ajoute `PayrollPayment.receiptNumber`, même méthode que `multi_tenant_schools` : diff généré avec `prisma migrate diff`, complété à la main d'un bloc `DO $$` de rétro-remplissage par école pour les 6 versements déjà existants avant d'ajouter la contrainte `NOT NULL`/l'index unique) → `registration_codes` (27/08, table `RegistrationCode` pour la vérification email à l'inscription) → `offline_first_operations` (28/08, mode hors-ligne : supprime `Payment.paymentNumber` — redondant avec `receiptNumber`, jamais affiché — et ajoute `clientOperationId` unique sur `Payment`/`Expense`/`PayrollPayment`/`SalaryAdvance`) → `remove_offline_first` (29/08, retire `clientOperationId` des 4 tables — mode hors-ligne entièrement abandonné à la demande de l'utilisateur, voir journal du 29/08 ; la suppression de `Payment.paymentNumber` par la migration précédente reste en place, décision indépendante toujours valable) → `number_sequence` (29/08, ajoute `NumberSequence` — compteur dédié par école/série pour les numéros de reçus, voir §14 ; écrite à la main sur le même modèle que `registration_codes`, table neuve sans rétro-remplissage nécessaire).

- Dashboard temps réel (aucune donnée fictive), refondu le 25/08 : grille de 6 cartes cliquables (Solde de caisse, Encaissé, Impayés, Élèves actifs, Personnel actif, À traiter), un panel « Finances », puis Élèves par classe et Statut des frais. Pas de carte « Présents aujourd'hui ». **Navigable par mois** (flèches ‹ › en haut de page, `GET /api/dashboard/summary?month=YYYY-MM`) : Solde (cumulé à la fin du mois choisi), Encaissé/Attendu/Dépenses/Salaires, Impayés (échéance dans le mois), Statut des frais et Élèves par classe (effectif reconstitué à partir des dates d'inscription/sortie) suivent tous le mois affiché. Élèves actifs, Personnel actif et À traiter restent volontairement figés sur « aujourd'hui » quel que soit le mois parcouru — l'app n'a pas d'historique daté pour ces états (pas d'`AuditLog`), donc pas de reconstitution honnête possible ; documenté à l'écran par une note sous les cartes.
- Réinitialisation complète possible : seed réduit au strict bootstrap (aucune donnée métier de démo), interfaces de création d'année scolaire et de type de frais désormais disponibles pour qu'une base vide reste utilisable.
- **Bulletin de salaire imprimable (27/08)** : chaque versement de salaire (`PayrollPayment`) a désormais un numéro (`receiptNumber`, format `BUL-<année>-<00001>`, scopé par école) et une page dédiée `/payslips/:paymentId` (`receipt-page.tsx`, `PayslipCard`/`PayslipPage`) — en-tête école (nom/adresse/téléphone, mêmes `Settings` que le reçu élève), employé, mois, détail salaire de base/primes/avances déduites/retenues/net, mode de paiement, encaisseur, bandeau d'annulation si versement annulé. Accessible via un bouton « Voir le bulletin » dans la modale « Versements » de la page Salaires (`PayrollPaymentsModal`, `phase7-pages.tsx`).
- **Multi-tenant / inscription en libre-service (25/08)** : écran « Créer une école » sur la page de connexion (`apps/frontend/src/App.tsx`, `LoginPage`), 3 champs (nom de l'école, email, mot de passe ≥ 8 caractères) → `POST /api/auth/register` crée l'école, l'admin, et connecte directement. Isolation vérifiée de bout en bout (voir §8) : deux écoles ne se voient jamais, numérotation des matricules/reçus indépendante par école, tentative de référencer l'ID d'une autre école (élève, classe, année…) rejetée en 400/404.

Composants UI partagés et réutilisés partout : `Modal`, `ContextMenu` (actions arbitraires), `SortHeader`/`useSortedRows`, `Field`, `CancelReasonModal`.

## 8. Décisions techniques importantes

- Montants de mensualité/assurance fixés **par élève** (`Student.monthlyFee`/`insuranceFee`), pas globalement par `FeeType` — décision explicite de l'utilisateur le 24/08 après confusion répétée sur l'origine d'un montant dû (voir `sections/2026-08-24-frais-eleves.md`).
- Pattern UI standard pour toute nouvelle page de liste : tableau triable + fenêtre modale de création/édition + menu contextuel clic droit — à réutiliser (composants §6), pas à réinventer.
- Toute opération financière : annulation à motif obligatoire, jamais de suppression ni modification libre (règle §37 du cahier des charges, appliquée strictement à Paiement/Dépense/Salaire/Avance).
- Tout handler frontend qui modifie une donnée financière doit appeler `loadData()` (recharge caisse/impayés/dashboard), pas seulement `loadFinance()` — un oubli a déjà causé un dashboard figé à 0 DH après encaissement (corrigé le 24/08).
- Convention de documentation : un fichier récapitulatif par module revu sous `sections/AAAA-MM-JJ-<nom>.md`, en plus du journal chronologique `job_day_date.md`.
- **Multi-tenant (25/08)** : isolation logique en base partagée (colonne `schoolId`) plutôt que des bases PostgreSQL physiquement séparées par école — choix assumé pour rester exploitable simplement sur un déploiement Docker Compose unique (une seule base à sauvegarder/migrer). `User.email` reste global (pas composite avec `schoolId`) pour que la connexion n'ait jamais besoin d'une étape « choisir son école ». `Role`/`Permission` restent un catalogue global, pas par école. Le scoping est centralisé dans une Prisma Client Extension (`tenant-db.ts`) plutôt que dans ~70 emplacements de requêtes édités à la main — bien plus sûr contre l'oubli d'un filtre, mais insuffisant seul : toute création acceptant un ID étranger doit en plus vérifier son appartenance à l'école (`assertOwned`), sans quoi l'extension timbre correctement le `schoolId` de la nouvelle ligne tout en acceptant une référence vers la ligne d'une **autre** école (la FK Prisma ne vérifie que l'existence, pas le tenant). La migration `multi_tenant_schools` a été écrite en partant du diff généré par `prisma migrate diff --from-url ... --to-schema-datamodel ... --script` (fiable pour la forme du DDL), puis complétée à la main d'un bloc `DO $$ ... IF EXISTS (SELECT 1 FROM "User") ... $$` qui rattache toutes les données pré-existantes à une école unique — la garde sur `IF EXISTS` évite qu'une base neuve reçoive une école fantôme avant que `seed.ts` ne fasse son propre bootstrap conditionnel (`School` vide → crée la première école depuis `ADMIN_EMAIL`/`ADMIN_PASSWORD`, sinon ne touche à rien).

## 12. Règles et conventions à ne jamais casser

- Ne jamais introduire `Float` pour un montant : toujours `Decimal`.
- Ne jamais supprimer physiquement un élève, un employé ou une opération financière validée — archivage/annulation uniquement.
- Ne jamais vérifier une permission uniquement côté React — toujours via `requirePermission` côté backend.
- Ne jamais écraser un versement/paiement existant — toujours en ajouter un nouveau et laisser l'historique intact.
- **Numérotation des opérations financières** : `Payment.receiptNumber`, `Expense.number`, `PayrollPayment.receiptNumber` sont générés **côté serveur** (`count()` scopé à l'école + 1, formaté `PREFIXE-<année>-<00001>`, séquentiel et sans trou par école) — voir §5. Un mode hors-ligne avec génération côté client (code appareil + `clientOperationId`) a été construit puis entièrement retiré le 29/08 à la demande de l'utilisateur (l'app reste volontairement « toujours connectée », voir journal du 29/08) — ne pas le réintroduire sans qu'il ne le redemande explicitement.
- Ne jamais coder en dur une URL, un port, un mot de passe ou un secret — toujours via `.env`/variables d'environnement.
- Toute nouvelle page de liste suit le pattern établi (tableau triable + modale + menu contextuel) en réutilisant les composants partagés existants plutôt qu'en les dupliquant.
- Ne pas changer la stack technique (React/Vite/Tailwind, Express/Prisma/PostgreSQL, Docker) sans accord explicite de l'utilisateur.
- Avant toute modification importante d'un module déjà en place, relire la section correspondante dans `sections/` si elle existe.
- **Multi-tenant — règle impérative** : toute nouvelle route backend touchant un modèle scopé par école (voir liste en §5) doit utiliser `request.db!` (client Prisma scopé, attaché par `authenticate()`), jamais `prisma` importé brut — sans quoi la donnée fuit entre écoles. Toute création acceptant un ID étranger fourni par le client vers un autre modèle scopé (`employeeId`, `academicYearId`, `schoolClassId`, `categoryId`, `guardianId`, `studentFeeId`, etc.) doit d'abord passer par `assertOwned(request.db, accessor, id)` avant d'écrire — l'extension de scoping ne bloque pas, à elle seule, la « plantation » d'un ID d'une autre école dans une nouvelle ligne. `prisma` brut ne doit servir que pour `School`/`Role`/`Permission` (catalogues globaux) et la recherche de connexion par email (avant qu'un `schoolId` soit connu).
- **Élèves — tous les champs obligatoires à la création** (26/08, voir journal) : le formulaire « Nouvel élève » n'a plus aucun champ optionnel (adresse, mensualité, assurance, classe, informations complètes du tuteur y compris email) — validé à la fois côté frontend (`required` HTML5) et côté backend (`POST /api/students`). Ne pas réintroduire de champ optionnel sur ce formulaire sans demande explicite de l'utilisateur ; si un nouveau champ est ajouté à cette fiche, il doit être obligatoire par défaut, pas optionnel.

## 14. Sauvegarde/restauration par école (terminé et testé le 29/08)

- **Objectif** : chaque école (compte admin connecté) doit pouvoir télécharger une sauvegarde de ses propres données, et plus tard la réimporter en cas de perte de données — sans jamais toucher aux autres écoles de la base partagée (§5/§8).
- **Export terminé et testé le 29/08** : `GET /api/backup/export` (`apps/backend/src/backup-routes.ts`, `requirePermission('backup.manage')`, nouvelle permission seedée à ADMIN) télécharge un fichier JSON — bouton « ⬇ Sauvegarder mes données » dans Paramètres (`apps/frontend/src/App.tsx`, `SettingsPage`).
- **20 tables exportées** (celles listées comme scopées par école en §5) + `StudentGuardian`/`PaymentAllocation` (filtrées via leur parent scopé, pas de `schoolId` propre) + `School.name` en métadonnée. Logique de construction centralisée dans `apps/backend/src/backup.ts` (`buildSchoolBackup`), pensée pour être réutilisée telle quelle par la future sauvegarde de sécurité pré-restauration.
- **Volontairement exclus** (décision validée avec l'utilisateur le 29/08) : `User`/`UserSession` (comptes/mots de passe — éviter d'exposer des hashs dans un fichier téléchargeable, et éviter de risquer l'auto-déconnexion de qui restaure), `RegistrationCode` (artefact de pré-inscription), catalogue global `Role`/`Permission`/`RolePermission`.
- **Format du fichier** : enveloppe `{ type: "schooldesk-backup", version: 1, schoolId, schoolName, exportedAt, tables: { ...20 clés... }, checksum: "sha256:<hex du JSON.stringify(tables)>" }`. Les `Decimal` Prisma se sérialisent en chaînes (ex. `"310"`), les `Date` en ISO — round-trippables tels quels pour une future restauration. Nom de fichier : `schooldesk-backup-<nom-école-slugifié-sans-accents>-<AAAA-MM-JJ>.json`.
- **UUID conservés tels quels** dans l'export (décision validée) — la restauration future ne les régénérera pas, pour garder toutes les clés étrangères intactes sans remapping.
- **Testé réellement le 29/08** : export vérifié de bout en bout via l'API sur une école jetable (structure vide) et sur la vraie école « YASSER » (7 élèves, 26 paiements, 32 mouvements de caisse — comptes du fichier vérifiés identiques aux comptes SQL réels), checksum recalculé et confirmé identique, 401 confirmé sans authentification. École/session de test nettoyées après coup, aucune donnée réelle touchée.
- **Restauration — implémentée et testée le 29/08** : `POST /api/backup/restore` (`apps/backend/src/backup-routes.ts`), `requirePermission('backup.manage')`. Corps `{ confirmName, backup }`, body parser dédié (`express.json({ limit: 25 Mo })`) monté **avant** le `express.json()` global dans `server.ts` — sinon la limite par défaut (100 Ko) rejetterait toute vraie sauvegarde avant même d'atteindre la route. Le dossier `storage/backups` est désormais un **volume Docker nommé** (`backups_data`, `docker-compose.yml`) — sans ça les sauvegardes de sécurité auraient été perdues à chaque recréation du conteneur, ce qui aurait vidé leur utilité.

- **Contexte** : l'utilisateur a tenté d'accéder à l'app depuis son téléphone connecté au même Wi-Fi que son PC (test légitime, distinct des captures d'écran de simulation utilisées jusqu'ici pour le responsive). ### 2026-08-28 — Suite : le menu ⋮ débordait de l'écran sur un item long (« Marquer comme parti… ») — repositionnement mesuré après rendu

- **Contexte** : capture d'écran réelle immédiate montrant le correctif précédent insuffisant — sur la page Élèves, l'item « Marquer comme parti (changement d'école) » (le plus long libellé de menu de toute l'app) débordait du bord droit de l'écran, texte coupé net par le bord de la carte.
- **Cause** : le clamp anti-débordement de `ContextMenu` reposait sur une **largeur devinée à l'avance** (`window.innerWidth - 200`, un chiffre fixe) plutôt que sur la largeur réelle du menu une fois rendu — qui varie forcément d'un item à l'autre maintenant que `whitespace-nowrap` empêche tout retour à la ligne (ajouté à l'étape précédente). Un item aussi long que « Marquer comme parti (changement d'école) » dépasse largement les 200px supposés, d'où le débordement.
- **Réalisé** (`ContextMenu`, `pages.tsx`) : le menu est désormais positionné en deux temps — rendu une première fois invisible (`visibility: hidden`, via un `ref`) à la position brute du clic, sa largeur/hauteur réelle est mesurée après ce premier rendu (`getBoundingClientRect()` dans un `useLayoutEffect`), puis repositionné et rendu visible avec un clamp calculé sur sa **vraie** taille (jamais de dépassement possible, quelle que soit la longueur du libellé le plus long). Remplace le clamp à marge fixe, devenu insuffisant par construction dès qu'un item est plus large que prévu.
- **Tests effectués** : `docker compose build frontend` (aucune erreur) ; déploiement forcé, healthcheck vert ; vérifié dans le bundle déployé la présence de `getBoundingClientRect`.
- **Problèmes** : aucun résiduel connu. Cette approche (mesurer après un premier rendu caché, puis repositionner) est la solution robuste standard pour ce genre de popover à taille de contenu variable — ne devrait plus jamais déborder, quel que soit le texte affiché, contrairement aux deux tentatives précédentes basées sur des marges devinées à l'avance.
- **Prochaine étape recommandée** : redemander confirmation visuelle sur ce cas précis (« Marquer comme parti ») ; si bon, ce chantier responsive peut raisonnablement être considéré clos.

### 2026-08-28 — Rafraîchissement automatique multi-appareils (polling 15s) + mode hors-ligne évoqué mais différé

- **Contexte** : l'utilisateur, satisfait du responsive, a fait deux demandes distinctes dans le même message. (1) Que l'app reste utilisable **sans connexion internet**, avec synchronisation automatique vers la base dès la reconnexion. (2) Un problème concret observé : une modification faite sur mobile n'apparaît pas sur le PC tant que la page n'est pas rafraîchie manuellement — jugé « pas professionnel ».
- **Décision de traitement** : les deux demandes n'ont pas du tout le même poids. Le point (2) est un vrai bug d'expérience, tractable en quelques lignes (l'app ne réinterrogeait le serveur qu'au chargement initial ou après une action locale, jamais en arrière-plan). Le point (1) — un vrai mode hors-ligne avec écriture locale puis synchronisation — est un chantier d'architecture majeur et risqué pour une application financière : `Payment.paymentNumber`/`receiptNumber`, `Expense.number`, `PayrollPayment.receiptNumber` sont des séquences **strictement croissantes par école** (voir §5) — deux appareils créant chacun un paiement hors-ligne généreraient inévitablement des doublons ou des trous à résoudre au moment de la synchronisation, avec un vrai risque de corruption de données financières si ce n'est pas conçu avec soin (détection de conflit, réservation de plages de numéros, ou renumérotation différée). Plutôt que de se lancer dans une implémentation hâtive sur un point aussi sensible (règle §12 : ne jamais perdre/dupliquer une donnée financière), le point (1) a été traité comme une vraie décision d'architecture à discuter, pas comme un simple ticket — seul le point (2) a été implémenté cette session.
- **Réalisé pour le point (2)** (`apps/frontend/src/App.tsx`) : nouveau `useEffect` qui relance `loadData()` (le même chargement complet déjà utilisé partout ailleurs — années, classes, élèves, personnel, frais, dépenses, salaires, avances, caisse, dashboard, impayés) toutes les **15 secondes** tant qu'un utilisateur est connecté (`setInterval`, nettoyé à la déconnexion/démontage). Passe par un `useRef` (`loadDataRef`) pour toujours appeler la version la plus récente de `loadData` sans avoir à relancer l'intervalle à chaque re-rendu (évite le piège classique de closure obsolète avec `setInterval` + React). `loadData` ne touche jamais les champs de formulaire en cours de saisie (`values.studentFirstName` etc., des clés distinctes non concernées par le rechargement), donc ce rafraîchissement périodique ne devrait pas perturber un formulaire ouvert en cours de frappe.
- **Tests effectués** : `docker compose build frontend` (aucune erreur) ; déploiement forcé, healthcheck vert ; vérifié dans le bundle déployé la présence de `setInterval` et de la constante `15e3` (15000 minifié). Pas de test navigateur réel multi-appareils cette fois (Playwright indisponible, et il faudrait deux sessions simultanées pour l'observer) — mécanisme standard React (`useEffect`/`setInterval`/`useRef`), fiable par construction, mais le comportement observé en conditions réelles (PC + mobile côte à côte) reste à confirmer par l'utilisateur.
- **Non fait, à trancher avec l'utilisateur avant d'attaquer** : le vrai mode hors-ligne (point 1). Pistes possibles à discuter plus tard, du plus simple au plus risqué : (a) lecture seule hors-ligne uniquement (consulter les données déjà chargées, sans pouvoir créer/modifier tant que la connexion n'est pas revenue — sûr, mais ne répond qu'à la moitié du besoin) ; (b) écriture hors-ligne avec file d'attente et synchronisation différée (répond entièrement au besoin, mais demande une refonte non triviale : identifiants générés côté client au lieu de séquences serveur, détection/résolution de conflits, indicateur visuel de « non synchronisé », re-numérotation des reçus après coup). Recommandation : commencer par (a) si le besoin réel est surtout de pouvoir *consulter* une fiche élève en zone blanche, plutôt que (b) qui est un chantier de plusieurs jours à lui seul.
- **Prochaine étape recommandée** : confirmer avec l'utilisateur que le rafraîchissement à 15s résout bien le problème PC/mobile signalé ; discuter et trancher l'ampleur voulue du mode hors-ligne avant d'y toucher.

### 2026-08-28 — Mode hors-ligne (offline-first) : Paiements, Dépenses, Salaires, Avances

- **Contexte** : suite de l'entrée précédente — l'utilisateur a confirmé vouloir un vrai mode hors-ligne (écriture, pas seulement lecture), avec une exigence concrète clarifiée en discussion : un paiement encaissé sans réseau doit pouvoir être **imprimé immédiatement**, pas affiché avec un numéro provisoire « en attente ». Conception discutée et validée point par point avec l'utilisateur avant tout code (voir tours de conversation précédents) : numéro **unique et définitif dès la création**, généré sur l'appareil, jamais renuméroté ; un seul système de numérotation (plus de distinction en-ligne/hors-ligne) ; `clientOperationId` technique pour l'idempotence ; historique existant jamais modifié ; périmètre limité à Paiements/Dépenses/Versements de salaire/Avances pour cette première étape.
- **Décision qui en a découlé, validée par l'utilisateur** : `Payment` avait deux champs redondants (`paymentNumber` et `receiptNumber`, toujours générés avec le même compteur, seul `receiptNumber` étant réellement affiché quelque part) — supprimé `paymentNumber`, un seul numéro désormais, préfixe `PAY-`.
- **Format unifié** (en ligne ou hors ligne, toujours le même mécanisme) : `PAY-<année>-<code appareil>-<compteur sur 6 chiffres>`, ex. `PAY-2026-A3F1-000001`. Même principe pour `Expense.number` (`DEP-`) et `PayrollPayment.receiptNumber` (`BUL-`). Le **code appareil** (4 caractères, alphabet sans caractères ambigus `0/O/1/I/L`) est généré une seule fois par appareil/navigateur et conservé dans `localStorage` (`apps/frontend/src/offline/device.ts`), affiché à titre informatif sur la page À propos. Le **compteur** est local à l'appareil, continu (jamais remis à zéro), incrémenté à chaque paiement/dépense/bulletin créé sur cet appareil (`apps/frontend/src/offline/numbering.ts`) — **changement de fond à retenir** : ce n'est plus un compteur unique pour toute l'école (« le 42ᵉ paiement de l'école ») mais un compteur par appareil (« le 42ᵉ paiement de CET appareil ») ; l'unicité globale vient de la combinaison compteur + code appareil, pas du compteur seul. Les numéros déjà attribués avant ce changement (format `PAY-2026-00042` sans code appareil) ne sont jamais modifiés — ancien et nouveau format coexistent, distinguables par la présence ou non du code appareil.
- **Idempotence** : chaque paiement/dépense/versement/avance porte désormais un `clientOperationId` (UUID généré sur l'appareil, `apps/frontend/src/offline/numbering.ts`, colonne dédiée `@unique` sur les 4 modèles). Si la même opération est envoyée deux fois au serveur (ex. coupure réseau juste après l'envoi, nouvel essai automatique), les 4 routes concernées (`POST /payments`, `/expenses`, `/payrolls/:id/pay`, `/salary-advances` dans `finance-routes.ts`/`operations-routes.ts`) renvoient l'enregistrement déjà créé au lieu d'en créer un doublon. Un conflit sur le numéro lui-même (deux appareils ayant généré par malchance le même — improbable vu l'entropie du code appareil, mais possible) est détecté distinctement (code `RECEIPT_NUMBER_CONFLICT`, HTTP 409) plutôt qu'une erreur générique.
- **Mécanisme technique côté frontend** :
  - `apps/frontend/src/offline/outbox.ts` — file d'attente locale dans IndexedDB (librairie `idb`), une entrée par opération en attente d'envoi.
  - `apps/frontend/src/offline/sync.ts` (`drainOutbox`) — rejoue la file vers le serveur dans l'ordre, s'arrête dès qu'une vraie coupure réseau est détectée (pas la peine d'insister sur les suivantes), continue malgré une erreur de validation sur une opération précise (reste en file, visible, pas perdue).
  - `App.tsx` : nouvelle fonction `createFinancial` (parallèle à l'ancien `create`) utilisée par `createPayment`/`createExpense`/`payPayroll`/`createAdvance` — génère toujours le numéro + `clientOperationId` sur l'appareil avant l'envoi ; si la requête échoue pour cause réseau, met l'opération en file (`enqueueOperation`) au lieu d'échouer, avec un message explicite (« enregistré hors-ligne, sera synchronisé automatiquement »). Synchronisation automatique toutes les 20s + sur l'événement navigateur `online` (`trySync`/`trySyncRef`). Bandeau visible dans `AppLayout` quand des opérations sont en attente (« N opération(s) enregistrée(s) hors-ligne »).
  - **Reçu de paiement imprimable hors-ligne** (le cas concret discuté avec l'utilisateur) : `createPayment` construit un instantané complet du reçu (élève, tuteur, montant, numéro définitif) à partir des données déjà en mémoire sur l'appareil, le stocke dans `localStorage` (`sd_offline_receipt_<clientOperationId>`), puis navigue directement vers `/receipts/<clientOperationId>`. `receipt-page.tsx` (`ReceiptPage`) essaie d'abord le réseau, puis retombe sur cet instantané local si `/api/payments/:id` est injoignable — le reçu reste donc imprimable immédiatement, sans jamais dépendre du serveur. Nettoyé automatiquement de `localStorage` une fois la synchronisation réussie (`sync.ts`).
  - **PWA** (`vite.config.ts`, plugin `vite-plugin-pwa`) : app installable, app-shell (JS/CSS/HTML/icônes) précaché pour un chargement possible sans réseau dès la deuxième visite ; les lectures `GET /api/*` suivent une stratégie réseau-d'abord avec repli sur le dernier résultat connu (`NetworkFirst`, délai 4s), donc les pages déjà consultées restent lisibles hors-ligne sans code additionnel côté app — seules les écritures (POST/PATCH/DELETE) passent par le mécanisme de file décrit ci-dessus. ### 2026-08-29 — Correctif : l'heure des reçus de paiement affichait toujours 01:00:00

- **Contexte** : bug signalé par l'utilisateur avec un exemple précis — un paiement encaissé vers 02:17 le 29/08/2026 affichait « 29/08/2026 01:00:00 » sur le reçu (date correcte, heure toujours fixe). Demande explicite de tracer la cause exacte dans toute la chaîne (création → stockage → API → affichage) plutôt que d'ajouter un correctif de façade (ni heure fixe, ni simple +1h), et de vérifier avec un vrai test après coup.
- **Cause exacte trouvée** : le champ « Date du paiement » du formulaire « Nouvel encaissement » est un `<input type="date">`, qui ne fournit qu'un jour (`YYYY-MM-DD`, sans heure) — toujours prérempli avec `today()` donc toujours envoyé au serveur, jamais `undefined`. Côté backend (`finance-routes.ts`, `POST /payments`), ce texte était converti directement via `new Date(paidAt)` — or `new Date("2026-08-29")` (sans composante horaire) est **toujours interprété par JavaScript comme minuit UTC**, jamais minuit local. Stocké tel quel en base (`2026-08-29 00:00:00 UTC`), puis réaffiché côté navigateur (`receipt-page.tsx`, `toLocaleString('fr-FR')`) en heure **locale** : minuit UTC devient 01:00:00 dans un fuseau UTC+1 (Maroc) — d'où l'heure fixe observée, qui n'avait jamais aucun rapport avec l'heure réelle de la saisie, celle-ci étant perdue dès la construction de la date envoyée au serveur.
- **Bug secondaire trouvé au passage (même famille)** : le préremplissage du sélecteur de date lui-même (`today()` dans `pages.tsx`, plus deux occurrences équivalentes dans `App.tsx`) utilisait `new Date().toISOString().slice(0, 10)` — convertit d'abord en UTC avant de découper la date, ce qui peut renvoyer la **veille** plutôt qu'aujourd'hui pour quiconque saisit une opération peu après minuit dans un fuseau UTC+ (ex. 00:30 locale au Maroc = 23:30 UTC la veille). Corrigé par la même occasion (`localDateString()`, construite à partir des composantes locales de `Date`, jamais via une conversion UTC intermédiaire) — utilisé pour `paymentPaidAt` et `attendanceDate`.
- **Correctif appliqué** (`apps/frontend/src/App.tsx`, `createPayment`) : au lieu d'envoyer le jour choisi tel quel, le frontend combine désormais ce jour avec l'**heure/minute/seconde réelles au moment de la saisie** (`new Date(year, month-1, day, now.getHours(), now.getMinutes(), now.getSeconds(), now.getMilliseconds()).toISOString()`) avant l'envoi — construit une vraie date/heure locale puis la convertit correctement en UTC pour le transport, sans jamais utiliser d'heure fixe ni de décalage arbitraire. Si le jour choisi est aujourd'hui (cas par défaut), le résultat est exactement l'instant réel de l'encaissement, à la seconde près. Si l'utilisateur choisit délibérément une date antérieure (aucun sélecteur d'heure n'existe pour ce cas), l'heure de saisie réelle est conservée sur ce jour-là plutôt que de retomber sur minuit — évite que le même bug ne resurgisse pour une date antérieure.
- **Tests effectués — vérification réelle demandée par l'utilisateur, pas seulement relue** : `docker compose build frontend` (aucune erreur) ; redéployé. Test de bout en bout par appel API réel reproduisant exactement le calcul désormais fait par le frontend (le poste de développement est lui-même en UTC+1, confirmant le même contexte que l'utilisateur) : paiement créé avec `paidAt` calculé à 02:24:25 heure locale → vérifié en base PostgreSQL directe (`SELECT "paidAt" FROM "Payment"`) : `2026-08-29 01:24:25.839` (UTC, correct) → simulation exacte du rendu `receipt-page.tsx` (`new Date(paidAt).toLocaleString('fr-FR')`) : **`29/08/2026 02:24:25`** — heure, minute et seconde réelles, correspondant exactement au moment de la création, plus aucune trace de « 01:00:00 ». Ligne de test supprimée après vérification (paiement, allocation, mouvement de caisse, frais, session).
